# Инициатива, ожидание и защита (#60)

Источник — русский exe 3.0 (Бука); адреса — RVA. Порт: `battle/initiative.rs`
и методы `BattleState` в `battle/state.rs`. Перенесённые имена служили указателями
для поиска; выводы ниже проверены по телам функций и исполнением x86-кода.

## Выбор участника

`16f250` обходит список `battlefield+0xd4` в его исходном порядке. Отбрасывает
участников с нулевой численностью (виртуальный `+0x40`) и `unit+0xa8 != 0`
(действие в этом раунде уже завершено). Каждый следующий кандидат заменяет лучшего,
только если `1f2d30` (`moves_before`) возвращает true.

`1f2cc0` и встроенная в `1f2d30` формула приоритета:

```
p = effective_speed
if !bad_morale: p += 1000
if good_morale: p += 1000
if waiting: p = -p
```

В нативных полях `+0xa49` — поздняя фаза из-за плохой морали,
`+0xa4b` — сработавшая хорошая мораль, `+0xc08` — ожидание.
Разность приоритетов вычисляется 32-битным вычитанием с проверкой знака
(`1f2df3: sub`, затем `jns`), поэтому порт использует wrapping-арифметику,
включая редкие крайние входы фикстур. Обычные скорости значительно меньше 1000.

При одинаковом приоритете участник с той же стороны не вытесняет уже найденного.
Если стороны различны, выигрывает сторона, **противоположная последней выбранной**:
сравнение идёт с `battlefield+0x37c`. Конструктор устанавливает его в 1 (`16102f`),
поэтому изначально при равенстве предпочитается атакующий. При выборе значение
меняется на сторону выбранного участника (`1682e5..1682f4`); на границе раунда
оно не сбрасывается. Простая сортировка «скорость → атакующий → слот» неверна.
Порт сохраняет порядок участников своего `BattleState`; нативный алгоритм выдачи
ID и полное создание списка по-прежнему не восстановлены (#53).

## Мораль и новый раунд

`1f2c30` и сброс раунда `1ecfb0` берут `CombatRandom(0, unit_id, 0x1c) % 10`,
сохраняют в `unit+0xaf0`, обнуляют `a49/a4b/af4`. Значение `af4` отмечает,
что результат морали уже показан/зафиксирован. Функция `1f32c0` классифицирует:

- плохая: `9 - roll < -effective_morale`;
- хорошая: `roll < effective_morale`;
- иначе обычная.

Мораль ограничена -10..10 её отдельным геттером `1efbd0`; иммунитеты и эффекты
могут менять итог. Срабатывание здесь меняет очерёдность, а не даёт выдуманное
дополнительное действие и не отнимает ход. Побочные эффекты морали для атаки и
анимации не относятся к планировщику.

`BattleState::begin_initiative_round` требует эффективные скорость и мораль каждого
участника, включая героев и уже погибших: оригинальный сброс проходит весь список.
В текущем API результат морали фиксируется при начале раунда. Разрешение иммунитетов,
заклинаний/артефактов и боевые статы героев не подставляются из догадок; это входы
вызывающего. Нативные переходные состояния UI до показа анимации морали не моделируются.
`set_turn_speed` позволяет поменять эффективную скорость в середине раунда без
переброса морали. Изменение эффективной морали эффектами в середине раунда пока
потребует подключения жизненного цикла эффектов к сохранённому результату.

Сброс `1ecfb0` очищает признак завершённого действия и ожидание. Следующий участник
выбирается заново динамическим проходом. Автоматическое начало нового раунда и
проверка окончания боя остаются за вызывающим; `begin_next_turn()` возвращает `None`,
когда все доступные участники закончили действия.

## Ожидание

Команда `172d40` ставит `unit+c08 = 1` и снова выбирает участника, не помечая
действие завершённым. При обычных положительных скоростях отрицательные приоритеты
попадают после не ожидающих; среди ожидающих раньше выбирается **медленный**.
Плохая/хорошая мораль участвует и в этом обращённом порядке. Порт разрешает ждать
один раз за раунд; повторная команда отвергается без изменения состояния.

## Защита

Команда `172b40` ставит `unit+a38 = 1` и переводит действие в состояние завершения
(`battlefield+500 = 5`; путь `16b1b0` помечает `unit+a8 = 1`). Флаг снимается при
следующем выборе того же участника (`167e2f`), **не** на границе раунда.

В геттере бонуса защиты `1f1a80` компонент стойки (`1f1b08..1f1b46`) умножает
защиту на 1.25. Если есть эффект `0x1f`, затем ещё на 1.5; после каждого умножения
результат сохраняется в `f32`. Эффект `0x1f` остаётся явным входом:
`apply_defense_stance(id, resolved_defense, effect_1f)`. Остальные множители защиты
и полная команда урона здесь не реализуются (#68); бой-заглушка карты не изменён (#75).

## Состояние и снимки

`TurnQueue.initiative` хранит эффективные входы, бросок морали, ожидание, стойку и
последнюю выбранную сторону. Прежний `begin_round(&ids)` оставлен для явных фикстур;
он не включает правила ожидания/защиты. Нативный режим включается только через
`begin_initiative_round`. Пустые слоты не участвуют, погибшие не выбираются.

Новые события: `InitiativeStarted`, `Waited`, `Defended`, `TurnSpeedChanged`.
Снимок боя имеет **версию 2**; v1 отклоняется, это не импорт старых сохранений игры.
Загрузка проверяет ID/стороны, мораль и броски, воспроизводит RNG и изменения
метаданных инициативы по журналу. Перезапуск раунда, неверный набор ID/мораль,
ожидание без активного участника и повторное ожидание не меняют состояние.

## Сверка с exe

```sh
.venv/bin/python tools/testbench/initiative.py --exe bin/heroes4.exe \
  --out /tmp/initiative_vectors.tsv
cargo test -p h4-rules --test initiative --locked
```

**1 619 фикстур** сохранены в `tests/initiative_vectors.tsv` и проверяются без игры:

- 210 классификаций морали (-10..10 × все десять бросков), исполняются оригинальные
  ветви `1f32c0` и геттер морали; остановка перед сообщениями/созданием эффектов;
- 1200 сравнений пар с обеими сторонами, моралью, ожиданием, равенствами и крайними
  i32-значениями: полные `1f2d30` и `1f2cc0`;
- 160 выборов из списков, в том числе погибшие и завершившие действие: полный `16f250`;
- 12 последовательностей бросков на три раунда: полный `1f2c30` и настоящий боевой RNG;
- 24 битовых результата компонента защиты и блоки команд ожидания/защиты;
- 12 связанных цепочек по три раунда (3/5/7 участников): полный `1ecfb0`, RNG,
  классификация морали, выбор, нативные блоки ожидания/защиты, снятия стойки,
  обновления стороны и завершения действия. Проверяется каждый выбранный участник,
  приоритет и маска защищающихся. Rust загружается из снимка по ходу цепочки.

Виртуальные численность/скорость/сторона, способности и эффекты — входы фикстуры.
У сброса раунда нет артефактов; реальные правила эффектов, UI, полные команды
действий и анимации не исполняются. Высокоуровневую последовательность команд
задаёт стенд; сами сравнения, обход, RNG и указанные блоки работают из exe.
Отдельные тесты проверяют атомарность ошибок, динамическую скорость, гибель стека,
границы раунда, продолжение после загрузки и отказ от повреждённых метаданных.
С запущенным оригиналом визуально не сверялось.
