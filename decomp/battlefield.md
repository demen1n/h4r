# Поле боя: начальное исследование загрузчика

Проверено по локальному exe Буки 3.0, 31 октября 2026.
Это карта вызовов для дальнейшего разбора, а не спецификация формата.

## Подтверждённая цепочка

- RVA `184cb0`: загрузчик ресурса создаёт временный объект поля,
  вызывает `184610`, затем создаёт игровое представление через `185120`.
- RVA `184470`: конструктор выделяет отдельный объект карты проходимости
  (конструктор `183ff0`) и хранит ссылку на него в поле `+4`.
- RVA `184610`: читает четыре байта из потока, затем вызывает `1840e0`
  и `18dfd0`. Смысл первого числа ещё не подтверждён.
- RVA `1840e0`: читает параметры карты, вызывает инициализацию
  изометрической основы и загружает строки карты из потока.
- RVA `18dfd0`: читает двухбайтовое число записей группы изображений;
  внутренние записи имеют шаг `0x68` в памяти. Это размер объекта,
  его нельзя использовать как длину записи в файле.
- RVA `185120`: игровое представление сохраняет ссылку на карту
  проходимости и создаёт группу изображений из временного объекта.

## Осторожность с символами

Перенесённые имена функций требуют проверки: `184610` назван
`initialize_backdrop`, но фактически читает поток, а не принимает готовое
изображение. Вызов `1840e0` тоже декомпилирован с потерянными аргументами.
Порядок и размеры полей нужно восстановить по дизассемблеру и байтам ресурсов,
прежде чем писать читатель. Сгенерированный C оставлен в `/private/tmp`.

## Следующие проверки

1. Выгрузить все видимые `battlefield_preset_map` и определить варианты заголовка.
2. Восстановить параметры изометрической карты и длины строк по дизассемблеру
   `184610`/`1840e0`; проверить расход байтов на каждом ресурсе.
3. Сопоставить `18dfd0` с существующими читателями групп изображений.
4. Отдельно восстановить `combat_object`: поле проходимости и визуальные
   препятствия пока нельзя считать одной структурой.

## Структурный читатель (реализован)

`h4-formats::battlefield::BattlefieldPreset` принимает проверенный заголовок
`u32 × 6 = [1, 1, 102, 16, 1180, 1024]`. Первый параметр передаётся
вложенному читателю, но там перезаписывается; смысл двух единиц не установлен.
Остальные поля — число изометрических строк, шаг и размеры экранного прямоугольника.
Для этой геометрии `base_initialize` (`34db60`) даёт границы строки y:
`start = max(37-y, y-37, 0)`, `end = min(38+y, 166-y, 102)`.
Затем следуют 4838 байтов строк **в обратном порядке**, u16 числа слоёв
и обычные слои `Layer`. Иные заголовки пока отклоняются.

Проверка `cargo run -p h4-formats --example check_battlefields`: все 24 видимых
ресурса установленной игры (включая алиас Bridge.single), по одному слою,
без остатка. Смещение группы изображений — 4862. Читатель не ищет маркеры
в байтах: граница вычисляется из геометрии. Есть синтетическая проверка порядка
строк, всех усечённых префиксов, неподдерживаемого заголовка и хвоста.
Смысл значений карты и визуальное совпадение фона ещё не проверены.

## Просмотр ресурсов

`h4-battlefield` показывает слои фона в их координатах и выбранный
`combat_object` с кадровой частотой и смещением из ресурса. Желтый крест —
точка привязки. Проверен графический запуск и контрольный снимок Bridge.single
с объектом Bones.05. Это визуальная проверка декодирования, не сравнение с
боем оригинала; автоматической расстановки и правил проходимости здесь нет.

## Координаты и блокировка живой клетки

Дизассемблер `34db00` вычисляет экранный центр для (x,y):
`X = 590 + 16*(y-x)`, `Y = 512 + 8*(x+y-102)` при геометрии пресетов.
Название перенесённого символа `get_map_point` вводит в заблуждение:
по арифметике это преобразование из карты в экран. Краевые клетки могут
выходить центрами за границу изображения из-за округления границ строк.
В просмотрщике `G` включает сетку и привязку объекта к ближайшему центру;
при выборе показывается исходное значение карты. `H4_GRID=1` включает её сразу.
Сетка охватывает все записанные клетки, включая области вне рисунка моста;
она не изображает уже восстановленную маску доступного движения.

`183a10` (`t_battlefield_cell::is_blocked`) возвращает true, если:

- у байта +1 **живой клетки** установлен бит 4;
- либо есть объект, у которого виртуальный метод +0x5c возвращает false,
  метод +0x10 возвращает true и указатель объекта не совпадает с проверяемым.

Это перенесено в `h4-rules::battlefield::cell_is_blocked`. Результаты виртуальных
методов передаются явно: их смысл и вычисление ещё не восстановлены.
Флаг живой клетки пока не связан с байтом пресета. Проверка включает все
значения байта флагов, комбинации двух виртуальных ответов, исключение своего
объекта и наличие второго блокирующего объекта. Сверки в Unicorn пока нет.

## Применение пресета к живым клеткам (1 ноября 2026)

Найден потребитель байтов: RVA `162aa0`, switch `162bc4..162c2b`.
Проверено по дизассемблеру и исполнением оригинального x86-кода в Unicorn.
Это **коды наложения**, не битовые флаги и не высоты. Пресеты применяются
последовательно; размер и границы каждой строки должны совпасть с живым полем.
Несовпавшее поле/строка пропускается, без масштабирования.

Пусть `T` — первый байт живой клетки, `F` — байт +1, `C` — контекстный
байт (проверяется на ненулевое значение):

| Код | Изменение T | Изменение F |
| --- | --- | --- |
| 0 | нет | при C != 0: F \| 0x1c; иначе без изменений |
| 1 | 1 | (F & 0xe3) \| (C == 0 ? 0x10 : 0) |
| 2 | 1 | F & 0xe3 |
| 255 (-1) | нет | (F & 0xef) \| 0x0c |
| остальные | нет | нет |

`183780` записывает T = (terrain & 0x1f) | (second_argument << 5);
в обеих ветках аргументы равны (1, 0). Блокировка `183a10` проверяет F & 4:
255 блокирует, 1/2 снимают этот флаг, 0 сохраняет его либо устанавливает.
Код 0 нельзя показывать как гарантированно свободную клетку.
Названия остальных битов 0x08/0x10 здесь не предполагаются.

Источник C прослежен до `[shared_object + 0x20]` (младший байт), где
shared_object возвращает `10c610` из `[battlefield + 0xc0] -> +0x140`.
**Игровой смысл C пока не установлен**; `apply_preset_cell` принимает
`block_zero` явно. Это не полное создание поля из условий боя.
Две единицы заголовка по-прежнему не расшифрованы.

Стенд `tools/testbench/preset_cells.py` исполняет switch в неизменённом exe
и реальный вызов `183780`, останавливаясь перед продвижением цикла. Входы:
код, C и исходные T/F; геометрия, получение C и обход строк этим стендом
не проверяются. Проверяется SHA-256 и баланс стека. 3072 ответа оригинала
(все 256 кодов × два C × два T × три F) сохранены в
`h4-rules/tests/preset_cell_vectors.tsv` и сравниваются с Rust в CI.

Просмотрщик по G показывает красным код 255, зелёным 1/2, оранжевым 0,
серым прочие коды. Это действие отдельного наложения, без учёта объектов,
других пресетов и контекста; визуальная сверка с оригинальным боем ещё нужна.
