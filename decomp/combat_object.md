# Боевые объекты (`combat_object`)

Проверено 31 октября 2026 по Буке 3.0. Читатель `206aa0` вызывает
`206690` для свойств и `349930` для изображения. Перенесённое имя `write`
неверно: виртуальный метод потока `+0x18` читает байты.

| Поле | Формат |
| --- | --- |
| Версия | u16, 0–2 |
| Два свойства модели | u8 × 2 в v2; один u8 в v0/v1, общий для обоих |
| Дополнительный параметр | u8 |
| Частота анимации | u8; оригинал вычисляет период как 1000 / значение |
| Флаг | u8, оригинал преобразует в bool |
| Дополнительные свойства | пять u8, только v1/v2 |
| Тип объекта | u16 id и строка с u16 длиной, только v1/v2 |
| Изображение | image sequence без внешнего u16 обёртки actor_sequence |

Два первых свойства — размеры до разбиения на сегменты; первый из пяти
дополнительных байтов и флаг участвуют в статической блокировке (разбор ниже).
Смысл дополнительного параметра и остальных четырёх байтов пока не утверждается.
В v0 оригинал задаёт нулевые дополнительные свойства и тип 0x25.
В v1/v2 оригинал ограничивает id диапазоном 0–0x25 и разрешает имя типа
через таблицу; читатель сохраняет исходные id и имя, не выполняя это разрешение.

Встроенная последовательность начинается непосредственно с версии image sequence,
затем читается существующим общим кодом слоёв, кадров, теней и смещения.
Сама структура image sequence не менялась.

`cargo run -p h4-formats --example check_combat_objects`: **1048 видимых ресурсов**,
1042 v2, шесть v0, без остатка. v1 в установке не встретилась; её порядок полей
подтверждён ветвлением читателя и синтетическим тестом, но не настоящим ресурсом.
Интеграционный тест читает все объекты и декодирует все их слои.
Синтетический тест проверяет версии, смещение последовательности, все усечённые
префиксы, неизвестную версию и лишний хвост. Внешний вид с оригиналом не сверялся.


## Статическая блокировка и занимаемые клетки (1 ноября)

Цепочка по коду нашего exe:

- `238690` читает размеры из корня модели +0x20/+0x24. Для блокирующих
  моделей выбирает размер квадратного сегмента как НОД размеров; квадратная
  модель остаётся одним сегментом. Вытянутые модели разбиваются с шагом НОД.
  Неблокирующие модели без флага и с типом вне 0x23/0x25 дробятся с шагом 1.
- Сегмент получает копию корня в +0x70 через `239200`, размер в +0x90,
  смещения частей в +0x94/+0x98. При разбиении изображения обрезаются;
  пустые части не создаются. Поэтому прямоугольник размеров ресурса сам по
  себе не является доказанной маской блокировки.
- Живой стационарный объект хранит сегмент по +0xa0. Его интерфейс по +8
  возвращает размер из segment+0x90 (`4772a0`).
- Главный виртуальный метод +0x10 (`477620`) возвращает segment+0x74:
  первый дополнительный байт ресурса (`attributes[0]`), ненулевое = true.
- Главный +0x5c (`477660`) возвращает segment+0x8c (флаг ресурса), либо
  compound+0x25 при наличии составного объекта по +0x9c. Это значение
  заставляет проверку клетки пропустить объект. Конструктор составного
  объекта `2377f0` копирует исходное значение из модели; дальнейшие изменения
  составного объекта нужно учитывать отдельно.

`1fc340` создаёт маску одного сегмента размера n×n:

```
0 <= x,y < n
(2*x + 1 - n)^2 + (2*y + 1 - n)^2 <= n*n + 2
```

Это округлённая маска, не заполненный квадрат (у n=1..4 углы ещё входят,
у n=5 углы уже исключены). `f160` переводит координату в смещение относительно
целочисленной позиции сегмента и проверяет эту маску. `f100` вычисляет центр
в субклетках: (16*x + 8*n, 16*y + 8*n).

Реализация: `h4_rules::battlefield::CombatFootprint`, `PlacedObstacle`,
`BattlefieldGrid`. Графика в правилах не участвует. Сетка хранит наложения
и списки объектов; снимает только указанную идентичность при проверке,
сохраняет остальные блокирующие объекты и бит блокировки земли. Идентичности
отдельных сегментов различны, даже если они принадлежат составной модели.
Добавление с выходом за поле или переполнением координат отклоняется целиком.

`PlacedObstacle::from_square_model` поддерживает ресурсы, которые остаются
одним квадратным сегментом. Прямоугольные ресурсы теперь
разрешаются через `CombatObject::segments` (см. ниже); просмотрщик добавляет
каждый полученный сегмент с отдельной идентичностью.
Неблокирующие/пропускаемые статические ресурсы не добавляют блокирующих клеток.
Автоматическая расстановка из table.combat_obstacles, осадные изменения и
генератор исходной земли не реализованы.

Проверка `tools/testbench/obstacle_cells.py`:

- оригинальный конструктор маски: 18 размеров (0..16 и 32);
- оригинальные `239200`, `477620`, `477660` и `183a10`: 432 сценария
  с обычной и составной моделью, флагами 0/1/255, свойством 0/1/36/255,
  вторым объектом, исключением себя и битом земли;
- 4838 центров клеток через оригинальное преобразование `164b40`.

Ответы сохранены в обычных Rust-тестах; CI не требует exe. Модель сегмента
и составной override в фикстуре заданы явно; полный преобразователь изображений
`238690` и расстановка препятствий этими сценариями не проверяются.


## Разбиение изображения в `238690` (1 ноября)

Восстановлена полная ветка для исходного масштаба **1.0**. После выбора шага
(НОД или 1 по условиям выше) оригинал обходит x внешним циклом, y внутренним.
Координаты угла сегмента в изображении:

```
px = 16 * (y - x) - image.offset.x
py =  8 * (x + y) - parameter - image.offset.y
```

`parameter` — значение root+8 из читателя `206690`; здесь оно сдвигает
плоскость обрезания по вертикали. Это ещё не утверждение о его роли в остальных
подсистемах. Границы верхней половины расходятся на 2 пикселя за строку,
нижней — сходятся с тем же шагом. На внешних краях границы продлеваются
до края общей области слоёв, включая выступающие вверх и вниз части изображения.
Маска общая для всех кадров, базовых слоёв и теней. Тени участвуют в наличии
сегмента независимо от переключателя их показа.

Виртуальный crop `192f20` пересекает каждую строку слоя с маской, отбрасывает
прозрачные края (индекс 0 при глубине 1, нулевой alpha при глубине 4), сохраняет
дырки внутри. Особенность exe: после первых записанных пикселей пустые строки
тоже участвуют в горизонтальных границах, даже ниже последней видимой строки.
Пустой слой получает нулевую ширину в правом краю исходного слоя. Общая область
группы включает и такие слои; проверка создания сегмента — только её ширина.
Поэтому объединение нескольких пустых слоёв на разных позициях само может
дать сегмент. Это поведение сохранено, а не заменено проверкой видимых пикселей.

Сегмент хранит (x,y) в клетках (в exe +0x94/+0x98 содержат 16*x/16*y),
квадратный размер +0x90 и обрезанную последовательность. Её offset становится
`(-px, -(py + parameter))`; координаты самих слоёв сохраняются. Квадратная
модель, остающаяся целой, и модель с нулевым размером идут по отдельной ветке
без обрезания, даже с пустым изображением.

`tools/testbench/obstacle_segments.py` запускает настоящую `238690`, конвертацию
слоёв, crop и конструкторы сегментов. Перехватываются только стандартные сервисы
стенда (выделение/освобождение памяти); геометрия и изображение не подменяются.
200 сценариев: один/два слоя, прозрачность 1/4, сплошное изображение, дырки,
локальный фрагмент, отдельные пиксели, пустое изображение, прямоугольные,
квадратные и нулевые размеры, флаги, типы и смещения. Сверяются порядок,
размеры и позиции сегментов, offset последовательности, прямоугольники слоёв
и FNV-64 содержимого (индекс и alpha, с нормализацией прозрачного цвета).
Эталоны: `h4-formats/tests/fixtures/obstacle_segments.txt`; CI не требует игры.

Все 1048 установленных ресурсов проходят разбиение и декодирование результата:
**7021 сегмент, 553 ресурса с несколькими сегментами**. Защита читателя отклоняет
для разбиения координаты слоёв/offset за пределами ±16384 пикселей.
Другие масштабы, разрешение имени типа через таблицу, автоматическая расстановка,
динамика составных объектов и сверка с настоящим боем остаются отдельной работой.
