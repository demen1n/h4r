# Случайные числа (heroes4.exe rus-3.0)

Реализация: `crates/h4-rules/src/random.rs`. Адреса — rva, если не сказано «VA» (база 0x400000).

## Формула

Везде одна и та же формула, как у `rand()` из Microsoft C:
`state = state * 214013 + 2531011` (32 бита, с переполнением), результат — `(state >> 16) & 0x7fff`
(0..32767). В exe она вписана в код ~120 раз (константа `0x269ec3`), множитель собран сдвигами
(`*3, *4+1, <<4, +1, <<8, -1, *4+1` = 214013). **Подтверждено кодом.**

`rand()`/`srand()` из CRT (rva `4ed0af`/`4ed0a2`, состояние в per-thread data `+0x14`) тоже есть,
29 вызовов, в бою и правилах их нет — похоже, интерфейс и служебное. Не разбирал.

## Глобальный генератор `t_random_number_generator random`

- Один объект, состояние — u32 по VA `0xac2018` (`?random@@3Vt_random_number_generator@@A`
  в отладочном мапе, `random.obj`). Методы (`operator()()`, `operator()(int)`, `(int,int)`,
  перечисления…) везде заинлайнены; вынесенная копия `operator()()` — rva `36a70`.
- Засев: `random$init` (rva `3f31a0`) — `state = time(NULL)` (CRT `time`, rva `4ee85f`).
  **Подтверждено кодом.**
- Вторая запись состояния — rva `d496f`, внутри функции чтения сохранённой игры (после
  `write_replay_event_state_cache`, имени нет): значит, при загрузке сейва состояние
  восстанавливается. Откуда берётся значение — **гипотеза** (из файла сейва), не проверял.
- `operator()(n)` на сайте rva `24d39`: `rand % n` со знаковой коррекцией (для n = 4).
  Остальные формы не разбирал.

## Генератор боя (rva `203280`)

Бой не тянет «следующее» число. Объект лежит в `t_battlefield + 0x380`; функция
`roll(a, b, purpose)` (thiscall, `ret 0xc`) возвращает число из той же последовательности,
но **по вычисляемому индексу**. **Подтверждено кодом** (дизассемблер, не декомпилят):

```
m      = purpose < 30 ? battlefield_field_438 - 1 : 200   // rva 177e00: [this+0x438] - 1
key    = (b % m, purpose, a % m)                           // беззнаковое деление
count  = ++counters[key]                                   // std::map, новый ключ начинается с 0
index  = ((purpose + 44 * count) * m + b % m) * m + a % m  // 32 бита с переполнением
return output(step^(index+1)(seed))                        // (index+1)-е число последовательности
```

- 44 — число кодов назначения (в exe встречаются 0..0x2b), так что разные назначения
  не делят индексы.
- Кэш: каждое 128-е состояние запоминается в векторе (`[this+0x1c]`), чтобы не шагать от
  зерна каждый раз; на результат не влияет.
- Засев (rva `203430`): `seed` в `[this+4]`, счётчики сбрасываются. Вызывается из rva `173e7c`
  (подготовка поля боя, при ненулевом `[battlefield+0x374]`) значением **одного числа
  глобального генератора** (0..32767), и из rva `233bf5` (не разбирал; возможно, сетевой бой —
  зерно от хоста).
- Смысл: результат броска зависит только от зерна, участников, назначения и номера такого
  броска — не от порядка остальных бросков. Так сетевые клиенты и повторы видят одно и то же.
- Что такое `[battlefield+0x438]` — **не выяснено** (похоже на число участников/идентификаторов).

Известные назначения (40 мест вызова, коды и делители после вызова — `% 10`, `% 100`, `% 1000`):

| код | где | что |
| --- | --- | --- |
| 0 | rva `1ee240` | бросок урона: `a` = id цели, `b` = id атакующего, `low + r % (high-low+1)` на каждое существо (≥ 10 существ — 10 бросков × number/10) |
| 0x1b | rva `1f2879`, внутри `get_magic_resistance` (имя tier D) | удача цели против заклинания: `r % 10 < luck` → урон ×2/3; `r % 10 < -luck` → ×1,5 |
| 0x1c | rva `1f2c4a`, `1eb737`, `1ed087` | мораль: `r % 10` |
| остальные | 1–0x2b | не разобраны |

## Что это значит для сравнения с оригиналом

- Чтобы повторить бой оригинала один в один, нужно знать зерно боя (одно число 0..32767),
  `[battlefield+0x438]` и id существ. Зерно можно перебрать: всего 32768 вариантов.
- Глобальный генератор засевается временем — его можно задать, подменив `time()` в стенде.
- Где решается удача атакующего (режимы 1/2 в `modify_damage`) — пока не найдено.
